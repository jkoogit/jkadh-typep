## 1. 개요 및 목적 (Purpose & Governance)

본 문서는 JKADH AI 소프트웨어 개발 플랫폼의 소스코드 구현 과정에서 적용되는 **소프트웨어 디자인 패턴, 아키텍처 설계 의사결정(ADR), 기술적 검토 정보 및 장단점 분석**을 체계적으로 기록하고 관리하는 **개발학습용 및 엔터프라이즈 아키텍처 거버넌스 표준 문서**입니다.

- **비즈니스 로직의 패턴화**: 복잡한 공급자별(Google, OpenAI, Anthropic 등) 로직과 상태 전이, 룰 엔진을 일관된 디자인 패턴으로 표준화합니다.
- **적용 기능 라이프사이클 추적**: 각 패턴이 어떤 비즈니스 기능에 언제 적용되었고, 변경되거나 폐기(Deprecated)되었는지를 명시적으로 관리합니다.
- **개발팀 학습 및 지식 자산화**: 신규 입사자 및 개발자가 아키텍처 설계 의도와 트레이드오프(Trade-off)를 즉각 이해할 수 있도록 교육 레퍼런스를 제공합니다.

## 2. 디자인 패턴 등록 거버넌스 템플릿 규격 (Pattern Registration Standard)

모든 패턴은 다음 6대 필수 메타데이터 항목을 포함하여 등록되어야 합니다:

1. **패턴명 (Pattern Name)**: 공식 GoF/클라우드 디자인 패턴 명칭 및 분류 (생성/구조/행위/안정성)
2. **패턴 설명 및 설계 의도 (Description & Intent)**: 문제 배경 및 패턴 도입 이유
3. **구조 다이어그램 및 인터페이스 계약 (Structure & Contract)**: 핵심 인터페이스 및 클래스/함수 관계
4. **장단점 및 기술적 검토 (Pros & Cons, Trade-offs)**:
   - **장점**: 유지보수성, 확장성, 결합도 완화, 테스트 용이성
   - **단점 및 주의점**: 클래스/파일 수 증가, 오버헤드, 러닝커브
5. **대상 적용 기능 목록 (Feature Application Lifecycle)**:
   - 기능명, 모듈, 적용일자, 적용상태(`ACTIVE`, `DEPRECATED`, `PLANNED`), 적용취소일자, 담당자
6. **실제 구현 코드 레퍼런스 (Code Reference)**: 소스코드 위치 및 핵심 스니펫

### 3.1 [PAT-BEH-01] Strategy Pattern (전략 패턴)

#### 1) 패턴 개요 및 설계 의도
- **분류**: 행위(Behavioral) 패턴
- **설계 의도**: AI 공급자마다 판이하게 다른 토큰 쿼터 검증 방식(Type-A: 정량 Usage API, Type-B: 응답 헤더 파싱 또는 0-Token Probe Ping, Type-C: 로컬 LLM 핑)을 동일한 인터페이스(`ITokenQuotaChecker`) 뒤로 캡슐화하여, 새로운 AI 모델이 추가되어도 기존 호출자 코드의 수정 없이 전략 클래스만 추가할 수 있도록(OCP 원칙) 설계.

#### 2) 인터페이스 및 구조 다이어그램
```
                 ┌─────────────────────────┐
                 │   ITokenQuotaChecker    │
                 ├─────────────────────────┤
                 │ + checkQuota(account)   │
                 │ + getRecoveryEstimate() │
                 │ + supportsDirectApi()   │
                 └────────────┬────────────┘
                              ▲
       ┌──────────────────────┼──────────────────────┬──────────────────────┐
       │                      │                      │                      │
┌──────────────┐       ┌──────────────┐       ┌──────────────┐       ┌──────────────┐
│ GeminiQuota  │       │ OpenAiQuota  │       │AnthropicQuota│       │DeepSeekQuota │
│   Checker    │       │   Checker    │       │   Checker    │       │   Checker    │
├──────────────┤       ├──────────────┤       ├──────────────┤       ├──────────────┤
│ [Type-A API] │       │ [Type-A API] │       │ [Type-B Hdr] │       │[Type-B Ping] │
└──────────────┘       └──────────────┘       └──────────────┘       └──────────────┘
```

#### 3) 기술적 검토 및 장단점 (Trade-offs for Learning)
- **장점 (Pros)**:
  - **OCP(Open-Closed Principle) 완벽 준수**: 신규 AI 모델(예: Claude 4, Llama 3) 도입 시 기존 코드를 건드리지 않고 전략 클래스 1개만 생성하여 등록 가능.
  - **테스트 용이성(Testability)**: 가상 목(Mock) 전략 객체를 손쉽게 주입하여 429 Rate Limit, 500 에러, 네트워크 단절 시나리오를 단위 테스트에서 완벽히 시뮬레이션 가능.
  - **이원화 로직 격리**: Type-A의 실 API 호출과 Type-B의 헤더 추출 로직이 분리되어 유지보수 안전성 극대화.
- **단점 (Cons)**:
  - 전략 클래스의 개수가 늘어나 파일 단위 관리가 필요함. (Factory/Registry로 해소)

#### 4) 대상 적용 기능 라이프사이클 (Application Matrix)
| 적용 기능명 | 소속 모듈 | 적용일자 | 상태 | 적용취소일자 | 담당 아키텍트 |
|---|---|:---:|:---:|:---:|---|
| **AI 모델별 온디맨드 토큰 쿼터 검증** | `PLAT-MON-08` | 2026-08-20 | **`ACTIVE`** | - | 김대원 / 조정국 |

### 3.2 [PAT-CRE-01] Factory / Registry Pattern (팩토리 & 레지스트리 패턴)

#### 1) 패턴 개요 및 설계 의도
- **분류**: 생성(Creational) 패턴
- **설계 의도**: 모델 ID(예: `gemini-1.5-pro`, `gpt-4o`, `claude-3-5-sonnet`) 또는 공급자 식별자를 입력받아 이에 매핑되는 `ITokenQuotaChecker` 싱글톤 인스턴스를 안전하게 생성 및 반환.

#### 2) 기술적 검토 및 장단점
- **장점 (Pros)**:
  - 인스턴스 생성 로직을 단일 진입점(`TokenQuotaCheckerFactory`)에 은닉하여 호출자의 의존성을 최소화.
  - 동일 모델에 대한 전략 객체 재사용(Flyweight/Singleton)으로 메모리 할당 방지.
- **단점 (Cons)**:
  - 팩토리에 신규 모델을 매핑하는 등록 절차가 필요함.

#### 3) 대상 적용 기능 라이프사이클
| 적용 기능명 | 소속 모듈 | 적용일자 | 상태 | 적용취소일자 | 담당 아키텍트 |
|---|---|:---:|:---:|:---:|---|
| **모델별 QuotaChecker 동적 라우팅 및 팩토리** | `PLAT-MON-08` | 2026-08-20 | **`ACTIVE`** | - | 김대원 / 조정국 |

### 3.3 [PAT-RES-01] State & Circuit Breaker Pattern (상태 및 서킷 브레이커 패턴)

#### 1) 패턴 개요 및 설계 의도
- **분류**: 안정성(Resilience) 및 행위(Behavioral) 패턴 (Martin Fowler Circuit Breaker)
- **설계 의도**: AI 공급자 장애(연속 실패 3회 또는 429 Quota Exceeded) 발생 시 시스템 전체의 연쇄 지연을 차단하기 위해 상태를 `CLOSED` ➔ `OPEN` ➔ `HALF_OPEN`으로 전이시키고 자동 차순위 폴백을 트리거함.

#### 2) 상태 전이 다이어그램
```
  [ 정상 운영 ] ────────────────────────── (연속 에러 3회 / 429) ─────────┐
       │                                                                  │
       ▼                                                                  ▼
 ┌───────────┐                                                      ┌───────────┐
 │  CLOSED   │ ◄─────────── [ 헬스체크 1건 성공 ] ─────────────── │   OPEN    │
 └───────────┘                                                      └─────┬─────┘
                                                                          │
                                                                 (쿨다운 60초 경과)
                                                                          │
                                                                          ▼
                                                                    ┌───────────┐
                                                                    │ HALF_OPEN │
                                                                    └───────────┘
```

#### 3) 기술적 검토 및 장단점
- **장점 (Pros)**:
  - **장애 격리 (Fail-Fast)**: 이미 소진되었거나 죽은 AI 공급자로의 불필요한 HTTP 통신을 원천 차단하여 사용자 응답 속도를 0ms로 단축.
  - **자동 복구 (Self-Healing)**: 쿨다운 타이머와 연동하여 사람의 개입 없이 `HALF_OPEN` 상태에서 헬스체크 후 정상 복구.
- **단점 (Cons)**:
  - 쿨다운 주기 및 실패 임계치 설정에 대한 정밀한 튜닝이 요구됨.
